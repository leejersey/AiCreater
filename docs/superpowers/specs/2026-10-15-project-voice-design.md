# Project-level voice settings

Approved by user m01683 after proposed project-level voice selection. No speed, clone, paid audition, ledger, hard budget or final20-case acceptance.

- Persist nullable public `{resource_id,speaker}` in projects.voice, additive idempotent migration. Legacy projects inherit configured default until explicit save, then pin resource and user-entered public speaker ID; no global .env writes. Server validates ASCII provider ID1–200 and project revision; initial outline generation must finish/cancel before settings change.
- Settings save is free and atomic under project lock, increments only project revision; no scene/audio/state/version/task changes. Same pinned value is idempotent. Form is public voice ID entry with current value and permission caveat, not an invented provider catalog or key field. Existing audio stays old; new setting alone does not generate/revoice.
- Effective profile used for new voice/timing jobs, voice publication fence and new version/preview metadata. Generation/candidate-model requests retain current behavior (no TTS there). Worker and explicit retry already use immutable frozen input; old jobs remain unchanged and may finish with unattached result if current voice no longer matches. No old result overwrites new setting's audio.
- Existing implicit-default batch policy remains compatible. For explicitly pinned project voice, batch dedup requires matching effective profile so old voice cannot be reused, and matching terminal jobs still never auto-retry. Share lookup between actual batch submit and readonly quote. Single-voice canonical hash likewise uses effective profile. Existing audio alone is not a free revoice.
- Reuse LocalDraft/DraftNotice and page dirty/busy protections; add scoped voice draft (project-only), explicit free-save confirmation, restore/discard/409 preserves input. Old API missing voice fields shows disabled pending-activation message rather than editing a fake default. No automatic audition or submit side effects.
- Inline implementation/TDD; isolated PostgreSQL/API tests and controlled independent production browser. Original DB/schema and supervised runtime remain untouched until separately safe activation. No extra dependency or Git initial commit; repository is unborn.
